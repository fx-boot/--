## BACKLOG-B19 · 驱动层提交结果反查通道未落地

- **编号**：BACKLOG-B19（源自 B19）
- **问题现象**：提交后结果不明（页面响应超时、未抓到平台任务 ID）时，`verifySubmission()` 恒返回 `found: false`，任务只能落「提交结果待确认」，需要人工到平台页面核对。
- **代码位置**：`app/src/workbench-dola-driver.js` → `async verifySubmission()`（v0.6.11 约 L2420）；调用方 `app/src/workbench-runner.js` L482–L483。
- **影响范围**：**低风险**。不影响核心业务（不重复提交、不改状态、不消耗额外额度）；仅影响「结果不明」场景的自动化程度与人工核对成本。命中概率取决于平台响应稳定性。
- **建议修复时机**：v0.6.12 做**只读骨架**（先读证据、不启用自动判定），待真实链路取得页面结构证据后再启用。
- **预估工作量**：`M`（驱动层 1 个方法 + 2–3 条离线断言 + 1 条人工验证用例）
- **修复思路**：
  1. 仅做**只读**匹配：按账号会话读取最近一条用户消息，用「提交时的请求指纹」（发送时间窗口 + 参考图张数 + 提示词长度/前缀哈希）与候选消息比对；
  2. 返回结构沿用现状 `{ found, platformTaskId, evidence }`，新增 `evidence.candidates` 便于人工核对；
  3. 命中歧义（多条候选）一律返回 `found:false` 并标注歧义，**不得**自动关联。
- **验收标准**：离线断言覆盖「唯一命中 / 无命中 / 多命中（拒绝关联）」；实现内**没有任何提交或点击发送的动作**（纯读取）；现有 `unconfirmed` 流程不变。
- **风险与对策**：页面结构变化会导致匹配失效 → 匹配失败时保持现有行为（落人工），不抛错、不重试提交。

## BACKLOG-B20 · 驱动步骤写库错误被静默吞掉

- **编号**：BACKLOG-B20（源自 B20）
- **问题现象**：任务执行过程中，把「驱动步骤」写进任务记录失败时没有任何痕迹，界面可能缺少部分步骤，排障时无法判断「是没执行」还是「执行了但没记录」。
- **代码位置**：`app/src/workbench-runner.js` L375–L385（`writeChain` 链尾 `.catch(() => {})`）。
- **影响范围**：**低风险**。仅影响可观测性（调试信息完整性）；不影响任务状态机、不影响提交与下载结果。
- **建议修复时机**：v0.6.12。
- **预估工作量**：`XS–S`
- **修复思路**：在链尾累计 `stepWriteFailures` 计数并记录最近一次错误消息，落进 `record.driver`/`record.poll`；任务卡片在计数 > 0 时显示「步骤记录写入失败 N 次（不影响任务状态）」。
- **验收标准**：注入一个写库失败（离线测试用假 taskStore）后，计数与被吞错误可见；正常路径计数为 0。

## BACKLOG-B21 · `cancel()` 在 pending 竞争失败时递归自调用

- **编号**：BACKLOG-B21（源自 B21）
- **问题现象**：对「待执行」任务点取消时，若与队列准入发生竞争（状态已被推进），代码会递归再调用一次 `cancel()`，极端并发下可能重复走取消流程。
- **代码位置**：`app/src/workbench-runner.js` → `cancel()` 的 `PENDING` 分支（patch 未取消则 `return cancel(projectId, attemptId)`）。
- **影响范围**：**低风险**。已有幂等保护（终态直接返回），最终状态正确；仅多一次读改写。
- **建议修复时机**：v0.6.12。
- **预估工作量**：`XS`
- **修复思路**：改为**有限重试**（最多 2 次，带 150–300ms 间隔），或直接返回当前记录并说明「状态已推进，未取消」。
- **验收标准**：离线断言「并发下最多重试 2 次」；取消语义与文案不变。

## BACKLOG-B22 · 自动重试退避起点语义偏松

- **编号**：BACKLOG-B22（源自 B22）
- **问题现象**：自动重试的退避使用 `Math.pow(2, performed)`，首轮 `performed = 0`，即第一次重试就按基准值（默认 8 秒）等待，而不是随重试序号递增。
- **代码位置**：`app/src/workbench-runner.js` L567。
- **影响范围**：**低风险**。自动重试仅对「明确未受理 + 临时可恢复」触发，且上限 2 次；节奏偏紧但不会重复扣费。
- **建议修复时机**：v0.6.12。
- **预估工作量**：`XS`
- **修复思路**：明确以「已排定重试次数」为指数（第 1 次 8s、第 2 次 16s），并把实际等待时长写入 `autoRetry.nextAt` 文案，便于用户预期。
- **验收标准**：断言两档退避值；`autoRetry` 展示与实际等待一致。

## BACKLOG-B23 · `library.templates` 未做字段归一化

- **编号**：BACKLOG-B23（源自 B23）
- **问题现象**：项目文件中的 `library.templates` 数组原样透传，异常/超长/类型错误的字段会一直留在项目里，并可能让资料库界面渲染异常。
- **代码位置**：`app/src/workbench-store.js` L97（`templates: Array.isArray(input.library?.templates) ? input.library.templates : []`）。
- **影响范围**：**低风险**。仅资料库模板；不影响项目、分集、素材、任务主数据。
- **建议修复时机**：v0.6.12。
- **预估工作量**：`S`
- **修复思路**：白名单归一化模板结构（如 `id/name/prompt/params{model,duration,ratio}/refs/createdAt`），字段截断（名称 ≤120、提示词长度上限）、条数上限（默认 200 条），非法条目计数并丢弃；对旧数据向后兼容（缺字段补默认值）。
- **验收标准**：断言「非法字段被剥离 / 超限被截断 / 旧数据可读」；资料库界面在污染数据下不报错。

## BACKLOG-B24 · `readIndex` 静默过滤非法 id

- **编号**：BACKLOG-B24（源自 B24）
- **问题现象**：项目索引中 id 不合法的条目被静默丢弃，界面上项目消失，但磁盘目录仍在（用户无从得知）。
- **代码位置**：`app/src/workbench-store.js` → `readIndex()`（`if (!ID_RE.test(text(p?.id))) continue;`）。
- **影响范围**：**低风险**。仅在索引被外部改动等极端场景出现；v0.6.11 已具备「索引损坏 → 从磁盘重建」兜底（B3），可恢复可见性。
- **建议修复时机**：v0.6.12。
- **预估工作量**：`S`
- **修复思路**：过滤时记录被忽略条目数与样例 id，写入 `recoveryInfo`；`storageStatus()` 暴露；界面在数据目录处提示「有 N 条索引项 id 非法，已忽略（目录保留）」并提供「从磁盘重建索引」按钮（复用 B3 通道）。
- **验收标准**：断言「非法条目被忽略但计入报告」；界面提示文案可见；重建后项目恢复。

## BACKLOG-B25 · 统一 IPC 异常丢失 `code`/`stack`

- **编号**：BACKLOG-B25（源自 B25）
- **问题现象**：IPC 包装层把任何异常统一转成 `new Error(message)` 抛出，错误码与堆栈丢失，前端只能按文案判断，无法按错误码分流（例如区分「参数不可提交」与「存储不可写」）。
- **代码位置**：`app/src/workbench-service.js` L685–L689（`throw new Error(state.lastError)`，v0.6.11 约 L688）。
- **影响范围**：**低风险**。不影响正确性，只影响前端错误处理精度与诊断效率。
- **建议修复时机**：v0.6.12。
- **预估工作量**：`S`
- **修复思路**：确立轻量错误协议：抛出前把 `error.code` 编码进消息前缀（如 `[INVALID_PARAMS] 原文`）或返回结构化 `{ ok:false, error:{ code, message } }`；先在 baseHandlers 落地，前端挑 1–2 处（提交前校验、素材删除）按 code 分流作为示范，其余保持文案展示。
- **验收标准**：断言「带 code 的错误经 IPC 后 code 仍可取得」；现有文案不回归（用户可见文字不变）。
