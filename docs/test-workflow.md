# 自测发现 Bug 后的迭代流程

> **前置材料**：[`v0.6.11-自测指引.md`](v0.6.11-自测指引.md)（怎么测）、[`test-bug-report-template.md`](test-bug-report-template.md)（怎么记）、[`backlog-issues.md`](backlog-issues.md)（已有遗留项）、[`git-branch-guide.md`](git-branch-guide.md)（分支与 tag 规范）、[`v0.6.12-plan.md`](v0.6.12-plan.md)（下一版范围）。
> **一句话**：**阻断/高 → 立刻修，发 v0.6.11 补丁版；中/低 → 进 backlog，随 v0.6.12 发布。**

---

## 一、流程总览

```
本地自测（按自测指引 ①→④）
        │
        ├─ 无问题 ──────────────────────────────► 记录通过 → 结束（可进入正式使用）
        │
        └─ 发现问题
             │
             ▼
      ① 按模板录入缺陷单（BUG-YYYYMMDD-序号）
         · 先判断是否命中已知遗留项 B19–B25（backlog-issues.md）
         · 判定严重等级（阻断 / 高 / 中 / 低，就高不就低）
             │
             ├── 阻断 / 高 ──► ②A 补丁流程（v0.6.11.x）
             │                  停止本轮测试 → hotfix 修复 → 离线断言 → 打包 → tag → 小范围回归
             │
             └── 中 / 低 ────► ②B 归入 backlog → v0.6.12 迭代
                               写入 backlog-issues.md（编号从 BACKLOG-B26 起）→ 纳入 v0.6.12-plan 的 P1/P2
             │
             ▼
      ③ 修复后由**原提单人复测**（同步骤、同环境），复测通过才关闭
             │
             ▼
      ④ 收尾：更新文档（用例/backlog/RELEASE）、补断言、Git 提交与 tag
```

---

## 二、分流规则

| 严重等级 | 判定要点（详见 bug 模板） | 处置路径 | 版本去向 |
|---|---|---|---|
| **阻断** | 打不开/数据丢失错乱/重复提交（可能扣费）风险/删除保护失效/版本号不符 | **立即停止自测**，当天进入修复；修复范围最小化 | **v0.6.11 补丁版**（`v0.6.11.1`，必要时 `.2`） |
| **高** | 核心流程不可用但数据未损坏；提示与行为严重不符 | 优先修复，与阻断项同批处理 | **v0.6.11 补丁版**；若影响面小且当前无批量使用，可并入 v0.6.12（需在单据中说明并确认） |
| **中** | 功能可用但结果不对、必要提示缺失、重启后状态不符预期 | 记入 `backlog-issues.md`，在 v0.6.12 排期时统一领取 | **v0.6.12** |
| **低** | 文案/样式/间距/悬停等外观体验问题 | 同上，可与 v0.6.12 的 UI 打磨项合并 | **v0.6.12**（可再顺延） |

**升级/降级规则**：测试人初判 → 维护者复核（允许改级，需在单据「影响与处置建议」里写明理由）；出现争议**就高不就低**。

## 三、路径 A：阻断 / 高严重 → v0.6.11 补丁版

**严格顺序（缺一步不得发布）**

1. **冻结现场**：暂停自测；复制一份 `isolated-data` 与缺陷单一起留存（脱敏后）。
2. **建分支**：`git checkout -b hotfix/v0.6.11.1 <对应 tag v0.6.11>`；只改与缺陷直接相关的代码。
3. **修复 + 断言**：修复同时补一条离线断言（并入 `tools/workbench-crud-guard.test.cjs`），三套离线测试全绿。
4. **红线复核**：不得触碰「只有 `pending` 才提交 / 未知状态转人工 / 下载失败不改生成」；并把 diff 里与缺陷无关的改动剔除。
5. **版本号**：`app/version.json` → `version: 0.6.11.1`，`notes` 写本次修复内容（把 0.6.11 的 notes 归档进 `history`）。
6. **提交**：`fix(<scope>): BUG-YYYYMMDD-xx <中文摘要>`；文档同步（RELEASE.md 追加补丁小节、用例补充）。
7. **打包**：`tools/pack-app.cjs` → 校验（asar 自检 + `baseline-verify` + 静态 35 项）→ 生成 `_build-v0.6.11.1\`（程序目录 + UTF-8 zip + 打包清单）。
8. **打 tag 并推送**：`git tag -a v0.6.11.1 <本次提交> -m "…（包内 gitCommit=…）"`；`git push origin main` + `git push origin v0.6.11.1`。
9. **回归（最小但必须）**：**原提单人**用同步骤复测；并跑一遍阻断级用例（EDG-02/03/04/06/07、BAT-04、UX-06）。
10. **通告**：给出补丁版「修复了什么 / 影响谁 / 是否需要重新下载」，附新包 SHA256 清单。

**补丁版边界**：只修「阻断/高」，**不夹带新功能、不夹带 backlog 项**（避免回归面扩大）。

## 四、路径 B：中 / 低 → 归入 backlog，随 v0.6.12

1. **按格式补录**：在 `docs/backlog-issues.md` 的汇总表与明细中各加一条，编号延续 **`BACKLOG-B26`、`B27`…**；必填字段：
   - 编号 / 标题 / 现象（可复现步骤）
   - 代码位置（符号名优先，行号标「以当版源码为准」）
   - 影响范围（明确写「不影响数据安全 / 额度安全」或相反）
   - 建议修复时机（默认 v0.6.12）
   - 预估工作量（`XS/S/M/L`，不承诺日历工期）
   - 修复思路 + 验收标准
   - 关联缺陷单号（BUG-YYYYMMDD-序号）
2. **纳入排期**：在 `docs/v0.6.12-plan.md` 的 §1.1 表格追加行（若与某条 UI 打磨相关，则并入 §1.2）。
3. **同步用例**：若该问题是既有用例没覆盖到的场景，在 `docs/v0.6.11-手动测试用例.md` 补一条对应用例（编号续 EDG/UX/BAT 段），保证下次能测到。
4. **关闭时机**：v0.6.12 修复并验证后，把 backlog 该条状态改为「已修复（v0.6.12）」。

---

## 五、复测与关闭口径（两条路径共用）

- **复测人**：必须是**原提单人**（避免「修的人说修好了」）。
- **复测内容**：① 原步骤不再复现；② 相邻功能未被改坏（该模块的冒烟用例）；③ 涉及数据的问题，需在**重启后**再次确认状态正确。
- **关闭条件**（三者齐全才关闭）：
  1. 缺陷单填写「复测结论：通过（日期 / 复测人）」；
  2. 对应的离线断言已入库且全绿；
  3. 修复已提交（含提交号）并（如发布）已打 tag。
- **未通过**：回到修复步骤，**不要**降级等级或改判「偶发」了事；连续两次修复未通过时，升级为「阻断」处理并暂停其它改动。

---

## 六、证据与合规要求（每次都要）

1. **额度红线**：自测与复测全程只允许「提交前校验（不发送）」；**若某缺陷必须在真实生成下才能复现** → 单独评估、单独授权后再做，且不顺带跑其它用例。
2. **脱敏**：缺陷单与截图中不得出现账号 id、Cookie、登录态、视频直链、真实素材原图。
3. **可追溯**：每张缺陷单必须能被追溯到「用例编号 + 版本号 + 提交号（或 tag）」；补丁必须能被追溯到「缺陷单号」。
4. **不在 `main` 上直接乱提交**：所有修复走 `feature/` 或 `hotfix/` 分支，合并前保证离线测试全绿（见 `git-branch-guide.md`）。

---

## 七、与后续版本的衔接

| 场景 | 动作 |
|---|---|
| 自测全过 | v0.6.11 可进入正常使用；遗留项（B19–B25）按 `v0.6.12-plan.md` 推进 |
| 出现阻断/高 | 先出补丁版；补丁修复不影响 v0.6.12 的范围，但**优先于** v0.6.12 的一切开发 |
| 出现中/低 | 进 backlog；若集中在某模块，v0.6.12 排期时可将该模块的打磨项提前（在 plan 里调整 P1/P2 顺序） |
| 缺陷暴露的是「已知遗留项」 | 直接用 BACKLOG 编号跟踪，不新开 BUG 单；但在单据里注明「命中 BACKLOG-Bxx」并补充新证据 |

---

*本流程为执行规范，不含代码改动；v0.6.11 交付产物与已发布包保持原样。*
